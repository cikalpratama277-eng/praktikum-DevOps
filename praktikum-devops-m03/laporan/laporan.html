2. Dasar Teori Ringkas

Git menyimpan snapshot, bukan selisih. Tiap commit menyimpan snapshot utuh; berkas yang tak berubah tidak disalin ulang melainkan dirujuk. Semua data dibangun dari tiga objek yang di-hash (SHA-1) dari isinya:

ObjekFungsi
blobIsi berkas (konten mentah, tanpa nama/path).
treeStruktur folder: nama berkas + pointer ke blob/tree lain.
commitPointer ke tree, pointer ke parent, penulis, waktu, pesan.

Karena tiap commit menunjuk parent-nya, riwayat membentuk DAG. Konsekuensi: (1) integritas terjamin — ubah 1 byte → seluruh hash turunan berubah (penting untuk audit trail/IaC); (2) operasi cepat — branching hanya membuat pointer, dasar seluruh strategi branching Minggu 4.

Tiga area kerja

Staging memungkinkan commit atomik (satu commit, satu perubahan logis) — mempercepat revert/bisect, berdampak langsung pada MTTR (metrik DORA Minggu 1).

5. Jawaban Pertanyaan Analisis (4.1)

5.1 Reset versus revert pada branch bersama

Bila rekan menjalankan git reset --hard + git push --force pada main yang sudah ditarik tiga anggota lain, ia memotong riwayat resmi. Kerusakan konkret pada salinan ketiga rekan: (1) commit yang mereka miliki kini "menggantung" (tidak ada di remote) sehingga git pull berikutnya menimbulkan divergensi/konflik dan memaksa rekonsiliasi manual; (2) pekerjaan lokal yang belum di-push berisiko terhapus saat mereka dipaksa menyelaraskan ke riwayat baru; (3) semua referensi commit (hash) setelah titik reset berubah, merusak tautan PR/CI yang menunjuk hash lama. git revert adalah satu-satunya pilihan tepat karena ia menambah commit pembatal (lihat Gambar 9) tanpa mengubah hash commit lama — remote tetap fast-forward, tidak ada yang kehilangan pekerjaan, dan efek commit perusak tetap ternetralkan.

Yang tidak dapat dipulihkan reflog: perubahan di working directory yang belum pernah di-commit lalu terkena reset --hard/restore. Alasannya, reflog hanya mencatat pergerakan HEAD (yakni commit-commit yang pernah masuk database Git); editan yang tak pernah di-commit tak punya objek di database sehingga tak ada yang bisa dirujuk kembali.

5.3 Kredensial yang terlanjur ter-commit

Token ter-commit 09.00 lalu berkasnya dihapus via commit baru 09.05 tetap dianggap bocor: menghapus berkas pada commit berikutnya tidak menghilangkannya dari riwayat — siapa pun yang meng-clone masih bisa git show/checkout commit 09.00 dan membaca token. Terlebih, begitu ter-push ke repo shared, harus diasumsikan bot crawler sudah memindainya. Urutan penanganan yang benar: (1) rotasi kredensial — cabut/nonaktifkan token lama & terbitkan yang baru; (2) baru bersihkan riwayat (mis. git filter-repo/BFG) & paksa sinkron; (3) perketat pencegahan (hook pre-commit, secret scanning). Urutan tidak boleh dibalik: bila membersihkan riwayat dulu tanpa rotasi, token yang sudah terekspos tetap sah dan dapat dipakai penyerang selama proses pembersihan berlangsung — rotasi mematikan nilai token seketika.

5.4 Ukuran commit dan kemampuan pemulihan

Pada repo saya, pola buruk yang dihindari adalah commit gabungan seperti "update tombol dan fix db" yang mencampur perubahan CSS & keamanan DB. Bila commit campuran semacam itu harus dibatalkan sebagian (mis. hanya bagian DB yang bermasalah), git revert akan ikut membatalkan perbaikan CSS yang sebenarnya baik — memaksa penyelesaian manual yang rumit dan rawan salah. Dengan commit atomik (Gambar 10: chore: dan docs: terpisah), pembatalan cukup menyasar satu commit. Kaitan MTTR: saat insiden produksi, commit kecil & fokus mempercepat identifikasi penyebab (git bisect) dan pemulihan (revert presisi), sehingga waktu pemulihan memendek.

5.5 Snapshot dan biaya branching

Dari git cat-file (Gambar 4–5): commit menunjuk tree berisi daftar blob; berkas README.md yang tak berubah memiliki hash blob identik di dua commit berurutan. Ini membuktikan Git menyimpan snapshot (keadaan utuh tiap commit) namun tidak boros: objek yang isinya sama hanya disimpan sekali dan dirujuk ulang (dedup berbasis hash). Karena membuat branch hanya menulis sebuah pointer 41-byte ke commit yang sudah ada — bukan menyalin berkas — operasinya nyaris tanpa biaya ruang/waktu. Sifat inilah yang membuat strategi branching intensif pada Minggu 4 (feature branch, GitFlow, trunk-based) praktis dilakukan.

7. Lampiran

Lampiran B.1 — hooks/pre-commit

#!/usr/bin/env bash
# .git/hooks/pre-commit — Gerbang Mutu: tolak kredensial + shellcheck .sh ter-stage.
set -euo pipefail
cred_pattern='ghp_[A-Za-z0-9]{20,}|AKIA[0-9A-Z]{12,}|-----BEGIN[A-Z ]*PRIVATE KEY-----|(PASSWORD|SECRET|TOKEN)[[:space:]]*=[[:space:]]*[^[:space:]]'
staged="$(git diff --cached --no-color || true)"
if printf '%s\n' "$staged" | grep -nEq "$cred_pattern"; then
  echo "pre-commit: DITOLAK — terdeteksi pola menyerupai kredensial:" >&2
  printf '%s\n' "$staged" | grep -nEi "$cred_pattern" >&2
  echo "Rotasi kredensial & keluarkan dari staging sebelum commit." >&2
  exit 1
fi
mapfile -t sh_files < <(git diff --cached --name-only --diff-filter=ACM | grep -E '\.sh$' || true)
if ((${#sh_files[@]} > 0)) && command -v shellcheck >/dev/null 2>&1; then
  if ! shellcheck "${sh_files[@]}"; then
    echo "pre-commit: DITOLAK — shellcheck melaporkan peringatan pada skrip ter-stage." >&2
    exit 1
  fi
fi
echo "pre-commit: seluruh pemeriksaan lolos."
exit 0

Lampiran B.2 — hooks/commit-msg

#!/usr/bin/env bash
# .git/hooks/commit-msg — wajibkan pola Conventional Commits.
set -euo pipefail
msg_file="$1"
header="$(head -n 1 "$msg_file")"
pattern='^(feat|fix|docs|chore|refactor|test)(\([a-z0-9_-]+\))?!?: .+'
if ! printf '%s\n' "$header" | grep -qE "$pattern"; then
  echo "commit-msg: DITOLAK — pesan tidak mengikuti Conventional Commits." >&2
  echo "  Jenis diizinkan: feat, fix, docs, chore, refactor, test" >&2
  echo "  Contoh benar  : 'feat(auth): tambahkan login'  atau  'fix: perbaiki bug'" >&2
  exit 1
fi
exit 0
