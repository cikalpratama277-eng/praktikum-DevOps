2. Dasar Teori Ringkas

DevOps adalah gerakan sosio-teknis yang meruntuhkan silo antara Development (dituntut cepat berubah) dan Operations (dituntut menjaga stabilitas). Konflik struktural ini melahirkan Wall of Confusion: kode "dilempar" melewati tembok organisasi disertai dokumen manual, lalu gagal di produksi dengan alasan klasik "it works on my machine". Budaya DevOps diringkas dalam akronim CALMS:

  • Culture — tanggung jawab bersama, budaya tanpa saling menyalahkan.
  • Automation — menghapus kerja manual berulang.
  • Lean — menghilangkan pemborosan pada aliran nilai.
  • Measurement — setiap keputusan berbasis metrik.
  • Sharing — pengetahuan milik tim, bukan individu.

The Three Ways: Flow (aliran cepat & searah, batch kecil, otomasi), Feedback (umpan balik cepat dari hilir ke hulu), dan Continual Learning (eksperimen aman + blameless postmortem). Keberhasilannya diukur objektif dengan empat metrik DORA:

PilarMetrikMakna
KecepatanDeployment Frequency (DF)Seberapa sering rilis ke produksi berhasil.
Lead Time for Changes (LTTC)Durasi dari commit hingga aktif melayani pengguna.
StabilitasChange Failure Rate (CFR)% rilis yang menyebabkan kegagalan/rollback.
Mean Time to Restore (MTTR)Rata-rata waktu pulih setelah insiden.

Riset DORA menunjukkan kecepatan dan stabilitas berkorelasi positif, bukan saling meniadakan — karena batch kecil lebih mudah diuji, ditinjau, dan dipulihkan.

3.3 JOB 3 — Value Stream Mapping: Mengukur Pemborosan

Seluruh langkah nyata pada JOB 2 diuraikan ke dalam Value Stream Map. Process Time (PT) = waktu kerja aktif bernilai tambah; Wait Time (WT) = waktu tunggu/antre (pemborosan); %C/A = persentase keluaran yang langsung dapat dipakai tahap berikutnya tanpa perbaikan.

Tabel 3.2 — Value Stream Map

NoAktivitasPelakuPT (menit)WT (menit)%C/A
1Menulis kodeDev8290%
2Menulis dokumen serah-terimaDev5340%
3Serah-terima artefakDev → Ops11050%
4Instalasi dependensiOps3530% ← bottleneck
5Perbaikan galat / klarifikasiOps6860%
6Verifikasi aplikasi berjalanOps11100%
TOTALΣ PT = 24Σ WT = 29—

Perhitungan Flow Efficiency

Flow Efficiency = Σ PT / (Σ PT + Σ WT) × 100%
               = 24 / (24 + 29) × 100%
               = 24 / 53 × 100%
               ≈ 45,3%

Hanya ±45% dari total waktu yang benar-benar bernilai tambah; sisanya (±55%) adalah pemborosan (menunggu & rework). Aktivitas dengan %C/A terendah = Instalasi dependensi (30%) merupakan bottleneck dan menjadi sasaran otomasi pada JOB 4.

5. Jawaban Pertanyaan Analisis (Bagian 4.1)

5.1 Analisis Akar Masalah

Kegagalan pada JOB 2 (3 galat, Lead Time 14 menit) bukan disebabkan kelalaian individu Developer, melainkan cacat desain sistem kerja. Buktinya: dokumen HANDOVER.md berbentuk prosa bebas yang tidak dapat diverifikasi mesin, sehingga siapa pun yang menulisnya akan cenderung menghilangkan langkah implisit (venv, pin versi, port) — kegagalan bersifat sistematis dan berulang, bukan kebetulan personal. Mengganti Developer tidak akan mengubah hasil karena kanal serah-terima itu sendiri yang cacat: searah, ambigu, dan tanpa umpan balik. Dua mekanisme sistemik yang mencegah kegagalan serupa meski personel diganti:

  1. Artefak yang dapat dieksekusi mesin (executable handoff). Mengganti dokumen prosa dengan setup.sh + requirements.txt terkunci memaksa setiap langkah tersembunyi menjadi eksplisit dan otomatis — terbukti menurunkan Lead Time menjadi ±1 menit dan kegagalan menjadi 0.
  2. Verifikasi otomatis wajib (health check / smoke test di pipeline). Endpoint /health + smoke test menjadikan "berhasil" terdefinisi objektif dan gagal terdeteksi < 1 menit, sehingga cacat tidak lolos ke hilir apa pun orangnya.

5.2 Evaluasi Klaim Otomasi

Klaim perusahaan bahwa mereka "ber-DevOps karena membeli Jenkins & Kubernetes" tidak valid. Memiliki perkakas bukanlah DevOps bila struktur tanggung jawab dan pengukuran tidak berubah. Adanya persetujuan manual manajer Ops rata-rata tiga hari untuk setiap deployment menunjukkan kegagalan pada:

  • CALMS — Automation: gagal. Gerbang persetujuan tetap manual; perkakas ada tetapi kerja manual berulang tidak dihapus.
  • CALMS — Lean: gagal. Antrean persetujuan 3 hari adalah pemborosan (wait time) murni pada aliran nilai.
  • CALMS — Culture: gagal. Persetujuan terpusat mencerminkan silo & ketiadaan tanggung jawab bersama.

Dari sisi DORA, penundaan 3 hari membuat Lead Time for Changes sangat panjang dan Deployment Frequency rendah — profil tim low performer. Perkakas hanyalah enabler; tanpa perubahan proses dan budaya, otomasi tidak menghasilkan Flow. Pilar yang gagal terutama Automation dan Lean (didukung kegagalan Culture).

5.3 Kuantifikasi Dampak

Dari Tabel 3.3, penghematan Lead Time per deployment = 14 − 1 = 13 menit. Untuk 20 deployment/bulan:

Penghematan kumulatif = 13 menit × 20 = 260 menit ≈ 4 jam 20 menit / bulan
Setahun               = 260 × 12       = 3.120 menit ≈ 52 jam / tahun

Namun angka waktu ini belum menggambarkan seluruh manfaat otomasi, karena metrik waktu tidak menangkap nilai kualitatif. Minimal dua manfaat yang tidak terukur oleh metrik waktu:

  1. Peningkatan keandalan & reproduktibilitas. Karena requirements.txt terkunci dan skrip idempotent, risiko kelas galat "it works on my machine" hilang — kualitas naik walau tak tampak pada stopwatch.
  2. Beban kognitif & moral tim. Ops tidak lagi menebak-nebak atau terganggu interupsi; energi mental dialihkan ke pekerjaan bernilai tambah, menurunkan risiko burnout dan kesalahan manusia.

(Manfaat lain yang juga tak terukur waktu: konsistensi lintas lingkungan, kemudahan audit/keamanan, dan skalabilitas onboarding anggota baru.)

5.4 Perbandingan Model SDLC Secara Kontekstual

Untuk sistem kendali perangkat medis yang wajib lolos sertifikasi regulator dengan syarat dokumentasi spesifikasi lengkap sebelum implementasi, model paling sesuai adalah Waterfall (atau V-Model sebagai variannya) pada tulang punggung siklusnya, karena sifat sekuensial & berorientasi dokumennya selaras dengan kebutuhan traceability dan pembekuan spesifikasi di awal.

Praktik DevOps yang tetap dapat diadopsi tanpa melanggar regulasi:

  • Automation pada CI & testing — build/test otomatis justru memperkuat bukti kualitas dan konsistensi untuk audit.
  • Infrastructure as Code & version control — meningkatkan ketertelusuran (setiap perubahan tercatat & dapat diaudit).
  • Blameless postmortem & monitoring — memperbaiki sistem tanpa mengubah gerbang regulasi.

Yang tidak dapat diadopsi apa adanya:

  • Continuous Deployment otomatis ke produksi — rilis ke perangkat medis memerlukan persetujuan/sertifikasi formal; deployment tak boleh sepenuhnya tanpa gerbang.
  • Deployment Frequency tinggi (rilis harian ke produksi) — bertentangan dengan siklus validasi regulator per rilis. (CI/CD boleh berhenti di staging; continuous delivery sampai siap-rilis diperbolehkan, tetapi continuous deployment ke perangkat produksi tidak.)

5.5 Trade-off Kecepatan dan Stabilitas

Berdasarkan pengalaman JOB 2 (manual, lambat, 3 kegagalan) dan JOB 4 (otomatis, cepat, 0 kegagalan), peningkatan Deployment Frequency tidak serta-merta menaikkan Change Failure Rate karena rilis yang sering memaksa batch size kecil: perubahan kecil lebih mudah diuji, ditinjau, dan dipulihkan. Otomasi + health check (seperti pada setup.sh) menangkap cacat sebelum ke produksi, sehingga kecepatan justru menurunkan risiko — persis temuan DORA bahwa kedua pilar berkorelasi positif.

Satu kondisi di mana asumsi ini tidak berlaku: bila frekuensi deployment dinaikkan tanpa otomasi pengujian yang memadai — mis. mempercepat rilis sambil melewati/menonaktifkan automated test dan health check. Dalam kondisi ini menaikkan DF akan menaikkan CFR karena cacat lolos ke produksi tanpa jaring pengaman. Kecepatan hanya aman bila ditopang otomasi kualitas & umpan balik cepat (The First & Second Way).

6. Kesimpulan

  • Pola serah-terima manual terbukti boros & rawan gagal: Lead Time 14 menit, 3 kegagalan, Flow Efficiency hanya ±45% (JOB 2–3).
  • Penerapan The First Way melalui setup.sh memangkas Lead Time ±93% menjadi ±1 menit, menghilangkan kegagalan & kebutuhan komunikasi manual (JOB 4).
  • DevOps adalah budaya + proses + pengukuran, bukan sekadar perkakas; kecepatan dan stabilitas berkorelasi positif bila ditopang otomasi & umpan balik.

Lampiran B — app-sentra/setup.sh (Zero-Touch)

#!/usr/bin/env bash
# setup.sh — Otomasi penyiapan & verifikasi aplikasi (The First Way: Flow)
#   ./setup.sh          Setup venv + install + jalankan + smoke test.
#   ./setup.sh --check  Validasi prasyarat saja (exit 0=siap, 1=tidak).
set -euo pipefail

APP_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
VENV_DIR="$APP_DIR/.venv"
PORT="${PORT:-5000}"
MAX_PORT_SCAN=20
HEALTH_RETRIES=5
HEALTH_DELAY=2

log()  { echo "[setup] $*"; }
fail() { echo "[setup] GAGAL: $*" >&2; exit 1; }

port_in_use() {                       # 0 = terpakai
  local p="$1"
  if command -v ss >/dev/null 2>&1; then
    ss -ltn 2>/dev/null | grep -q ":${p}[[:space:]]"
  else
    python3 - "$p" <<'PY'
import socket, sys
p = int(sys.argv[1]); s = socket.socket()
try: s.bind(("127.0.0.1", p)); sys.exit(1)
except OSError: sys.exit(0)
finally: s.close()
PY
  fi
}

find_free_port() {                    # cetak port bebas mulai $1
  local start="$1" p end; end=$((start + MAX_PORT_SCAN))
  for ((p = start; p < end; p++)); do
    if ! port_in_use "$p"; then echo "$p"; return 0; fi
  done
  return 1
}

check_prereq() {
  log "[1/5] Memeriksa prasyarat..."
  command -v python3 >/dev/null || fail "python3 tidak ditemukan."
  python3 -c 'import sys; sys.exit(0 if sys.version_info >= (3,10) else 1)' \
    || fail "dibutuhkan Python 3.10 atau lebih baru."
  python3 -m pip --version >/dev/null 2>&1 || python3 -m ensurepip >/dev/null 2>&1 \
    || fail "pip tidak tersedia dan gagal di-bootstrap."
  [ -f "$APP_DIR/requirements.txt" ] || fail "requirements.txt tidak ditemukan."
  log "Prasyarat terpenuhi (python3, pip, requirements.txt)."
}

if [ "${1:-}" = "--check" ]; then
  check_prereq
  if port_in_use "$PORT"; then
    log "Port $PORT sedang terpakai."
    if free_port="$(find_free_port "$PORT")"; then log "Port bebas: $free_port."
    else fail "tidak ada port bebas pada rentang $PORT-$((PORT + MAX_PORT_SCAN))."; fi
  else log "Port $PORT bebas."; fi
  log "SIAP: seluruh prasyarat lingkungan terpenuhi."; exit 0
fi

check_prereq
log "[2/5] Menyiapkan virtual environment..."
[ -d "$VENV_DIR" ] || python3 -m venv "$VENV_DIR"
# shellcheck source=/dev/null
source "$VENV_DIR/bin/activate"

log "[3/5] Memasang dependensi terkunci..."
pip install --quiet --upgrade pip
pip install --quiet -r "$APP_DIR/requirements.txt"

if port_in_use "$PORT"; then
  log "Port $PORT terpakai, mencari port bebas berikutnya..."
  PORT="$(find_free_port "$PORT")" || fail "tidak ada port bebas yang tersedia."
  log "Menggunakan port $PORT."
fi

log "[4/5] Menjalankan aplikasi pada port $PORT..."
PORT="$PORT" python3 "$APP_DIR/src/app.py" &
APP_PID=$!
trap 'kill "$APP_PID" 2>/dev/null || true' EXIT

log "[5/5] Melakukan smoke test (retry maks $HEALTH_RETRIES x, jeda ${HEALTH_DELAY}s)..."
ok=0
for ((i = 1; i <= HEALTH_RETRIES; i++)); do
  if curl -fsS "http://127.0.0.1:$PORT/health" >/dev/null 2>&1; then ok=1; break; fi
  log "  percobaan $i/$HEALTH_RETRIES belum berhasil, menunggu ${HEALTH_DELAY}s..."
  sleep "$HEALTH_DELAY"
done

if [ "$ok" -eq 1 ]; then
  log "SUKSES: aplikasi berjalan dan lulus health check (PID $APP_PID, port $PORT)."
else
  fail "aplikasi tidak merespons health check setelah $HEALTH_RETRIES percobaan."
fi
log "Aplikasi aktif di http://127.0.0.1:$PORT/  (tekan Ctrl+C untuk berhenti)."
wait "$APP_PID"

Lampiran B (lanjutan) — app-sentra/teardown.sh

#!/usr/bin/env bash
# teardown.sh — Menghentikan aplikasi & membersihkan .venv secara AMAN.
#   ./teardown.sh          Hentikan aplikasi (pertahankan .venv).
#   ./teardown.sh --purge  Hentikan + hapus .venv (dengan validasi path).
set -euo pipefail

APP_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
VENV_DIR="$APP_DIR/.venv"
PORT="${PORT:-5000}"
log() { echo "[teardown] $*"; }

stop_app() {
  local pids=""
  if command -v lsof >/dev/null 2>&1; then pids="$(lsof -ti tcp:"$PORT" 2>/dev/null || true)"
  elif command -v fuser >/dev/null 2>&1; then pids="$(fuser "$PORT"/tcp 2>/dev/null || true)"; fi
  if [ -n "$pids" ]; then
    log "Menghentikan proses pada port $PORT: $pids"
    # shellcheck disable=SC2086
    kill $pids 2>/dev/null || true; sleep 1
  else log "Tidak ada proses aktif pada port $PORT."; fi
}

purge_venv() {                        # hapus HANYA setelah validasi path
  [ -z "${VENV_DIR:-}" ] && { log "Batal: VENV_DIR kosong."; return 0; }
  if [ "$VENV_DIR" = "/" ] || [ "$VENV_DIR" = "$HOME" ]; then
    log "Batal: VENV_DIR menunjuk lokasi berbahaya ($VENV_DIR)."; return 1; fi
  case "$VENV_DIR" in
    "$APP_DIR"/.venv) : ;;
    *) log "Batal: VENV_DIR ($VENV_DIR) di luar direktori aplikasi."; return 1 ;;
  esac
  if [ -d "$VENV_DIR" ]; then
    log "Menghapus virtual environment: $VENV_DIR"; rm -rf -- "$VENV_DIR"
    log "Selesai membersihkan .venv."
  else log "Direktori .venv tidak ditemukan."; fi
}

stop_app
if [ "${1:-}" = "--purge" ]; then purge_venv
else log "Mode aman: .venv dipertahankan (jalankan dengan --purge untuk menghapus)."; fi
log "SELESAI."
